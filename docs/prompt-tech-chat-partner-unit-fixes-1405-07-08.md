# نقصِ ۱ — ابزارِ «درصدِ تغییرات» ضریب را برای همیشه از کار می‌اندازد

## شاهد

در `applyPricingPercent` اولین خطِ حلقه بی‌قیدوشرط است:

```js
rows.forEach(r => {
    if (bump(r, 'partnerUnitPrice')) touched++;
```

و سرور برای این فیلد همیشه پرچم را روشن می‌کند:

```java
case "partnerUnitPrice" -> {
    p.setPartnerUnitPrice(newVal);
    p.setPartnerUnitOverride(true);
}
```

پس یک بار اعمالِ درصد روی یک نما، **همهٔ ردیف‌های آن نما را «✋ دستی» می‌کند** و
ضریب دیگر هرگز رویشان نمی‌نشیند. ابزارِ درصد ابزارِ روزمرهٔ قیمت‌گذاری است (۱۵۵
تغییر در همین هفته)؛ یعنی بعد از اولین استفاده، کلِ کارِ ۷ عملاً خاموش می‌شود.

## کار

همان تفکیکی که قیمتِ سایت دارد (`formulaBased`) برای «همکار تک» هم بیاید:

- ردیفِ فرمولی (پرچمِ دستی ندارد و «فروش تعدادی» دارد و کاربر اجازهٔ ویرایشش را
  دارد) → درصد فقط روی «فروش تعدادی»؛ سرور «همکار تک» را خودش حساب می‌کند.
- ردیفِ دستی، یا بدونِ «فروش تعدادی» → درصد مستقیم روی «همکار تک».

تصمیم بگیر و در گزارش بنویس: برچسبِ «دستیِ درصدی» مثلِ `pricePercentAdjusted`
لازم است یا نه. اگر نساختی، دلیلش را بگو.

# نقصِ ۲ — پیش‌نمایش عددی نشان می‌دهد که ذخیره نمی‌شود

## شاهد

در `priceInput`:

```js
if (field === 'partnerUnitPrice' && !r.partnerUnitOverride
        && pricingDirty.has(`${r.id}|partnerBulkPrice`)) {
    ...
    rawShown = String(Math.round(b * pricingUnitFactor)); derived = true; pending = false;
}
```

این شاخه نگاه نمی‌کند که خودِ `partnerUnitPrice` هم در `pricingDirty` هست یا نه.
بعد از اعمالِ درصد هر دو هستند. نتیجه:

```
namayesh:  bulk_jadid x 1.05
zakhire:   unit_ghadim x (1 + darsad/100)   + parcham-e dasti
```

روی لوکال از ۷۳ کالایی که هر دو قیمت را دارند ۷۲ تا نسبتی غیر از ۱٫۰۵ دارند، پس
این اختلاف تقریباً روی همهٔ ردیف‌ها رخ می‌دهد.

## کار

عددِ نمایش‌داده‌شده همیشه همان باشد که ذخیره می‌شود. با رفعِ نقصِ ۱ احتمالاً خودش
حل می‌شود، ولی **جدا تستش کن**: یک ردیفِ فرمولی و یک ردیفِ دستی، هر دو با درصد،
عددِ خانه قبل از ذخیره را با عددِ دیتابیس بعد از ذخیره مقایسه کن.

# نقصِ ۳ — نقشِ فروش هم می‌تواند ضریب را عوض کند

## شاهد

`POST /api/v1/pricing/partner-unit-factor` قاعدهٔ اختصاصی در `SecurityConfig` ندارد
و زیرِ قاعدهٔ عمومی می‌افتد:

```java
.requestMatchers("/api/v1/pricing/**").hasAnyRole("ADMIN", "PRICER", "SALES")
```

در UI هم دکمه با `pricingCanEdit` نمایش داده می‌شود که برای هر سه نقش `true` است.
ولی «فروش تعدادی» سمتِ سرور برای SALES قفل است (`canEditPricerOnlyFields`)، و این
ضریب قیمتی را می‌سازد که از همان ستونِ قفل مشتق می‌شود. راهِ دورزدنِ قفل است.

## کار

- سمتِ سرور: فقط ADMIN و PRICER. SALES باید `403` بگیرد — با `curl` نشان بده.
- سمتِ UI: دکمه با `canEditBulkPrice` دیده شود، نه `pricingCanEdit`.
- `GET` برای هر سه نقش باز بماند (پیش‌نمایش لازمش دارد).
- `partnerUnitOverride` در `/batch` هم همین مرز را بگیرد: «بازگشت به فرمول» برای
  SALES مجاز است یا نه؟ حدس نزن — رفتارِ `priceOverride` را ببین و همان را بکن.

# نقصِ ۴ — اعتبارسنجیِ ضریب فقط در مرورگر است

```java
java.math.BigDecimal next = new java.math.BigDecimal(String.valueOf(body.get("factor")));
```

- بدنهٔ بدونِ `factor` رشتهٔ `"null"` می‌سازد و `NumberFormatException` می‌دهد؛ یعنی
  `500` به‌جای `400`.
- بازهٔ ۰٫۵ تا ۳ فقط در `Swal` چک می‌شود. درخواستِ مستقیم با `factor: 105` پذیرفته
  می‌شود و اولین ویرایشِ «فروش تعدادی» قیمتِ همکار را صدوپنج برابر می‌کند.

## کار

همان بازه سمتِ سرور، در `updatePartnerUnitFactor`، با `ApiException` و کدِ `400`.
مقدارِ نامعتبر و مقدارِ خالی هر دو `400` بدهند. تست بنویس.

# ⛔ منتظرِ تصمیمِ مالک — تا خبر نداده‌ام دست نزن

`recalcPartnerUnitIfDerived` هر ردیفی را که پرچمِ دستی ندارد فرمولی حساب می‌کند.
ولی عددهای «همکار تک»ِ موجود پیش از این قابلیت و با دست وارد شده‌اند و هیچ‌کدام
پرچم ندارند. پس اولین ویرایشِ «فروش تعدادی» آن‌ها را به ضرب در ضریب برمی‌گرداند.

دو راه هست و انتخابش بازرگانی است، نه فنی:

- **حفظ:** یک‌بار برای همهٔ ردیف‌هایی که عددشان با فرمول نمی‌خواند پرچمِ دستی
  گذاشته شود.
- **جایگزینی:** فرمول جای همه بنشیند.

هر کدام انتخاب شد، بندش به همین فایل اضافه می‌شود.
