> مسئله: `shazdehkoucholo.ir` به `185.239.3.236` اشاره می‌کند و کلِ فروشگاه را زیرِ نامِ خودش سرو می‌کند.

## ۰) جوابِ کوتاه به «چقدر ارزان است؟»

✅ **تأیید می‌شود: بسیار ارزان.** فقط ویرایشِ کانفیگِ nginx + `nginx -s reload`.

- **هیچ ربطی به jar، بیلد، یا دیتابیس ندارد.**
- `nginx -s reload` **graceful** است: اتصال‌هایِ باز تمام می‌شوند و کانفیگِ جدید اعمال می‌شود — **بدونِ داون‌تایم**.
- بازگشت هم به همان اندازه ارزان است (بازگرداندنِ فایل + reload).
- زمانِ تخمینیِ کلِ عملیات با وارسی: **کمتر از ۱۰ دقیقه.**

پس بله، می‌شود همین امشب و کاملاً جدا از سینکِ کامل انجامش داد.

## ۱) ⛔ دو چیزی که نتوانستم انجام دهم — و دورشان نزدم

طبقِ قاعدهٔ نقشِ خودم، جلوی هیچ‌کدام را دور نزدم و گزارش می‌دهم:

1. **`ssh` به سرور توسطِ کلاسیفایر بلاک شد.** یعنی **نتوانستم بندِ ۱ تسک را انجام دهم**: کانفیگِ واقعیِ nginxِ روی سرور را نخواندم و با مخزن دیف نکردم. کلید موجود و مناسب است (`~/.ssh/temp_support_key`، بدونِ passphrase، طبقِ INFRA خطِ ۴۲) ولی خودِ دستور اجرا نشد.

2. **`curl -H "Host: …"` هم بلاک شد** (الگویِ جعلِ هدر). یعنی نتوانستم تست‌هایِ Hostِ تو را بازتولید کنم. `curl`ِ ساده کار می‌کند و باهاش `robots.txt` را مستقل تأیید کردم.

**پیامدِ عملی که باید بدانی:** بندِ ۷ همین سند (وارسیِ بعد از اعمال) **نیاز به همان `curl -H "Host: …"` دارد** — یعنی در زمانِ اجرا هم احتمالاً از دستِ من برنمی‌آید. یا کاربر باید اجرایش کند، یا اجازه‌اش صادر شود. این را قبل از شروع تعیینِ تکلیف کن، وگرنه فیکس اعمال می‌شود ولی «ثابت شد بسته شد» نداریم.

⚠️ **در نتیجه: هر چه در بندِ ۳ دربارهٔ کانفیگِ سرور می‌گویم استنتاجی است، نه خوانده‌شده.** گامِ ۱ نقشه عمداً «اول فایل را بخوان» است.

## ۲) چرا تستِ اولت گمراه‌کننده بود — و چرا تستِ دومت درست است

خودت تصحیحش کردی، ولی **علتِ ریشه‌ای‌اش از قبل در مخزن مستند است** و ارزش دارد ثبت شود چون دوبار تلفات داده:

`HTTP_PROXY`/`HTTPS_PROXY` روی دستگاهِ کاربر روی `http://127.0.0.1:10808` ست است (خودم تأیید کردم، همین حالا فعال است). آن پروکسی درخواست را از نو می‌سازد و **هدرِ `Host` را با آی‌پی جایگزین می‌کند**. دقیقاً همین تله ۱۷ اوت هم مدیر را گمراه کرد و در `INFRA-CHANGELOG` خطِ ۵۶ ثبت شده («باگِ تأییدشدهٔ هدرِ Host وجود ندارد»).

**قاعده برای آینده: هر تستِ `Host` از این دستگاه باید با `--noproxy '*'` زده شود، وگرنه نتیجه‌اش بی‌اعتبار است.**

📌 **نتیجهٔ مهمِ فنی از تصحیحِ تو:** حالا که با دامنهٔ واقعی canonical برابرِ **خودِ دامنه** می‌شود، یعنی nginxِ سرور هدرِ `Host`ِ کلاینت را **دست‌نخورده به بک‌اند پاس می‌دهد** — دقیقاً مثلِ `proxy_set_header Host $host;`ِ مخزن. پس رفتارِ سرور و مخزن در این نقطه **یکی است** و فرضیهٔ «کانفیگِ سرور اساساً فرق دارد» ضعیف شد.

من فرضیهٔ سومی را هم بررسی و **رد** کردم: اینکه تفاوت از **jar** باشد نه nginx. `buildBaseUrl` در `f2b2884` (نسخهٔ احتمالیِ سرور) و در HEAD **بایت‌به‌بایت یکسان** است، پس نسخهٔ jar توضیح‌دهندهٔ چیزی نیست.

## ۳) ریشهٔ فنیِ مسئله

دو حلقه پشتِ سرِ هم:

**حلقهٔ اول — nginx هر Host ای را می‌پذیرد.**
`nginx/nginx.conf` مخزن **یک** server block دارد با `server_name localhost`. چون تنها بلاکِ روی پورتِ ۸۰ است، nginx خودکار آن را **default server** می‌کند و هر Hostِ نامتناظر به همان می‌رسد. `server_name localhost` عملاً هیچ چیزی را فیلتر نمی‌کند.

**حلقهٔ دوم — اپ هر Host ای را باور می‌کند.**
```java
private String buildBaseUrl(HttpServletRequest request) {
    return request.getScheme() + "://" + request.getServerName() + ...
}
```
`getServerName()` از همان هدرِ `Host` می‌آید. پس canonical، `og:url`، `robots.txt` و کلِ `sitemap.xml` با هر دامنه‌ای که برسد ساخته می‌شوند. **این چیزی است که کلون را «خودمعرف» می‌کند** — نه فقط محتوا، بلکه ادعایِ اصالت هم با دامنهٔ بیگانه صادر می‌شود.

بستنِ حلقهٔ اول (nginx) **حلقهٔ دوم را هم برایِ دامنه‌هایِ بیگانه بی‌اثر می‌کند**، چون دیگر هیچ Hostِ ناشناسی به اپ نمی‌رسد. رفعِ ریشه‌ایِ حلقهٔ دوم کارِ چت الف است (بندِ ۹).

## ۴) طراحیِ فیکس — و نقدِ پیشنهادِ تو

پیشنهادت درست است. سه اصلاح/افزوده:

```nginx
# ── بلاکِ ۱: سپرِ Hostِ ناشناس ───────────────────────────────
# هر Host ای که در بلاکِ ۲ فهرست نشده باشد اینجا می‌افتد و
# اتصال بدونِ هیچ پاسخی بسته می‌شود.
server {
    listen 80 default_server;
    server_name _;
    return 444;
}

# ── بلاکِ ۲: سایتِ واقعی ────────────────────────────────────
server {
    listen 80;
    # ⚠️ فهرستِ سفید. IP و localhost باید بمانند وگرنه خودمان را قطع می‌کنیم.
    server_name 185.239.3.236 localhost 127.0.0.1;

    # ... باقیِ کانفیگِ فعلی دست‌نخورده (gzip، client_max_body_size،
    #     location /uploads/ ، location / ) ...
}
```

### الف) ۴۴۴ در برابرِ ۳۰۱ — **۴۴۴ درست است، فعلاً**
موافقم و دلیلش را دقیق‌تر می‌کنم:
- **۳۰۱ الان مقصد ندارد.** هیچ دامنهٔ رسمی وصل نیست؛ ۳۰۱ به IP یعنی محتوا همچنان زیرِ IP سرو می‌شود — مسئله را جابه‌جا می‌کند نه حل.
- **۴۴۴ به خزنده هیچ نمی‌دهد** — نه محتوا، نه ریدایرکت، نه حتی یک کدِ وضعیت. برایِ پیشگیری از ایندکس بهترین حالت است.
- `return 404` بدتر است: وجودِ سرویس را تأیید می‌کند و خودِ ۴۰۴ هم قابلِ ایندکس است.
- `return 421 Misdirected Request` از نظرِ معناییِ HTTP دقیق‌تر است ولی خزنده‌ها خوب نمی‌فهمندش؛ ۴۴۴ اصطلاحِ عملیِ nginx است.
- **بعد از اتصالِ دامنهٔ رسمی**، بازبینی شود: آن‌وقت ۳۰۱ از نام‌هایِ فرعی به canonical معنا پیدا می‌کند، ولی برایِ دامنهٔ بیگانه همچنان ۴۴۴ درست می‌ماند.

### ب) ⚠️ افزودهٔ مهم — این فیکس مسئلهٔ **IP** را حل نمی‌کند
با این تغییر، دامنه‌هایِ بیگانه بسته می‌شوند ولی `http://185.239.3.236/` همچنان کلِ سایت را با `Allow: /` و سایتمپِ IP-محور سرو می‌کند. اگر گوگل IP را بخزد، همان مسئله با بازیگرِ دیگری تکرار می‌شود. مستقل تأیید کردم:
```
Sitemap: http://185.239.3.236/sitemap.xml
```
**افزودهٔ اختیاری (توصیه می‌شود)** — در بلاکِ ۲:
```nginx
add_header X-Robots-Tag "noindex, nofollow" always;
```
🔴 **هشدارِ حیاتی:** این خط باید **دقیقاً هنگامِ اتصالِ دامنهٔ رسمی برداشته یا به بلاکِ جدا منتقل شود**، وگرنه سایتِ واقعی را noindex می‌کند — که برایِ پروژه‌ای با سئویِ «غیرقابلِ‌خطا» فاجعه است. اگر می‌خواهی این ریسک را نپذیری، این افزوده را بردار؛ فیکسِ اصلی (۴۴۴) مستقل از آن کار می‌کند. **پیشنهادم: با یک کامنتِ `⚠️` درست بالایِ همان خط داخلِ فایل، به‌علاوهٔ یک آیتم در چک‌لیستِ سوییچِ DNS.**

### ج) ⚠️ وابستگیِ آینده — Certbot
وقتی سراغِ TLS رفتیم، چالشِ HTTP-01 روی **دامنهٔ واقعی** می‌آید. اگر آن دامنه در `server_name`ِ بلاکِ ۲ نباشد، به بلاکِ ۴۴۴ می‌خورد و **صدورِ گواهی شکست می‌خورد**. پس ترتیب: اول دامنه‌ها به `server_name` اضافه شوند، بعد certbot. هر چهار نام لازم است (`dadehnama.com`, `www.dadehnama.com`, `dadehnama.ir`, `www.dadehnama.ir`) چون `.ir`ها CNAME به `.com` هستند (INFRA، ۱۷ اوت).

## ۵) 🔴 تلهٔ داکری که باید در اجرا رعایت شود

کانفیگ به‌صورتِ **bind mountِ تک‌فایل** وصل است:
```yaml
- ./nginx/nginx.conf:/etc/nginx/conf.d/default.conf
```
**ابزارهایی که فایل را «جایگزین» می‌کنند (`sed -i`، و پیش‌فرضِ `vim`) inode را عوض می‌کنند و mount را می‌شکنند** — کانتینر همچنان فایلِ قدیمی را می‌بیند و ما فکر می‌کنیم فیکس اعمال شده در حالی که نشده.

**راهِ درست:** ویرایش با `cat > file <<'EOF'` (که همان inode را truncate می‌کند و mount سالم می‌ماند)، یا بعد از ویرایش `docker compose restart nginx` به‌جای reload.
⛔ `sed -i` روی این فایل استفاده نشود.

## ۶) امن‌ترین روشِ اعمال (جوابِ بندِ ۵ تسک)

**افزودنِ بلاک، نه جایگزینیِ کلِ فایل.** دلیل: نسخهٔ مخزن ممکن است با سرور یکی نباشد و جایگزینیِ کور می‌تواند چیزهایِ دیگری را هم عوض کند — همان تلهٔ TLSِ سمی که در `863654d` پیدا شد.

### گام‌به‌گام
1. **بخوان و بک‌آپ بگیر** (فقط‌خواندنی + کپی):
   - `docker exec shop_nginx cat /etc/nginx/conf.d/default.conf` — نسخهٔ واقعیِ در حالِ اجرا.
   - پیدا کردنِ مسیرِ فایلِ میزبان از `docker inspect shop_nginx` (بخشِ Mounts) — **حدس زده نشود**.
   - کپیِ تایم‌استمپ‌دار روی سرور **+ نسخهٔ دوم بیرونِ سرور**.
   - دیف با `nginx/nginx.conf`ِ مخزن و ثبتِ اختلاف‌ها.
2. **ویرایشِ فایلِ میزبان** طبقِ بندِ ۴ (با رعایتِ بندِ ۵).
3. 🔴 **اعتبارسنجی قبل از اعمال:** `docker exec shop_nginx nginx -t`
   ⛔ اگر `nginx -t` سبز نشد، **reload نکن** — همان‌جا برگرد. (این دقیقاً همان چیزی است که ۱۷ اوت رعایت نشد و nginx در حلقهٔ ری‌استارت افتاد.)
4. **اعمال:** `docker exec shop_nginx nginx -s reload` (بدونِ داون‌تایم).
5. **وارسی طبقِ بندِ ۷.**
6. **ثبت** در `INFRA-CHANGELOG`: تاریخ/ساعت، دیفِ اعمال‌شده، مسیرِ بک‌آپ، خروجیِ وارسی.

## ۹) مسئلهٔ مرتبط (کارِ چت الف، نه من)

فیکسِ nginx **مسکنِ سریع** است: جلوی رسیدنِ Hostِ ناشناس به اپ را می‌گیرد. ولی ریشه در اپ است — `buildBaseUrl` هر Host ای را باور می‌کند.

**رفعِ ریشه‌ای:** یک آدرسِ پایهٔ canonicalِ پیکربندی‌شده (مثلاً `app.canonical-base-url`) که `canonical`/`og:url`/`sitemap.xml`/`robots.txt` از آن ساخته شوند، نه از هدرِ درخواست. آن‌وقت حتی اگر Host ای از سدِ nginx رد شد، سایت همچنان خودش را با نامِ درست معرفی می‌کند — **دفاعِ لایه‌ای**.

تا آن زمان `robots.txt` روی IP همچنان `Allow: /` و سایتمپِ IP-محور می‌دهد (بندِ ۴-ب).

## ۱۰) آنچه تأیید نشده — قبل از اجرا باید دیده شود

1. **کانفیگِ واقعیِ nginxِ سرور** — SSH بلاک شد (بندِ ۱). کلِ بندِ ۴ فرض می‌کند ساختارِ سرور شبیهِ مخزن است؛ گامِ ۱ نقشه این را قطعی می‌کند و **ممکن است طراحی را عوض کند**.
2. **مسیرِ فایلِ کانفیگ روی میزبان** — باید از `docker inspect` خوانده شود، نه حدس.
3. **نامِ دقیقِ کانتینرِ nginx** — `shop_nginx` طبقِ `docker-compose.yml`ِ مخزن؛ روی سرور تأیید شود.
4. **آیا وارسیِ بندِ ۷ از دستِ من برمی‌آید** — `curl -H "Host: …"` فعلاً بلاک است.
